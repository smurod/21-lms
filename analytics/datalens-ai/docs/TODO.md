# Техническое задание на доработку datalens-ai

> Документ для AI-исполнителя в новой сессии.
> Внимательно прочитай `docs/INTEGRATION.md`, `docs/ARCHITECTURE.md`, `docs/API.md`,
> `docs/DATALENS_OBJECTS.md`, `docs/LLM_AND_PROMPTS.md`, `docs/TESTING.md` перед началом.
>
> **Главное правило:** публичный HTTP-контракт (`docs/API.md`) ломать нельзя.
> URL, методы и поля ответов `dashboard_id`, `dashboard_url`, `charts`, `added`,
> `updated`, `deleted` должны сохраняться.

## 1. Что уже реализовано

- Подключение к DataLens: логин, workbook `AI Generated`, поиск/создание.
- PostgreSQL-подключение с `raw_sql_level=dashsql` в нужном workbook.
- Анализ схемы БД:
  - таблицы/колонки/типы/PK/FK;
  - подсчет строк;
  - выбор ключевых таблиц по эвристикам и размеру.
- LLM-клиент к llama-server:
  - отключение thinking у Qwen3 (`enable_thinking=false`);
  - быстрый запуск через `start_llm.py`.
- Промпты в Markdown (`prompts/chart_one.md`, `chart_fix.md`, `editor_plan.md`).
- Генерация SQL по одному графику за запрос:
  - валидация `EXPLAIN`;
  - dry-run `LIMIT 5`;
  - автоисправление по ошибке БД;
  - отсев пустых запросов;
  - анти-зацикливание.
- QL-чарты `line`, `column`, `table` через `ql_chart_builder.py`.
- Сборка дашборда в 36-колоночной сетке (`dashboard_builder.py`).
- Полный цикл создания дашборда (`dashboard_service.py`).
- Редактирование дашборда (`ai_editor.py`):
  - `add`, `update`, `delete`, `reorder`;
  - пересборка layout после действий.
- FastAPI приложение (`main.py`) с endpoint'ами:
  - `POST /api/dashboards/generate`;
  - `GET  /api/dashboards/{id}`;
  - `POST /api/dashboards/{id}/edit`;
  - `GET  /api/charts/{id}`;
  - `POST /api/validate-sql`;
  - `GET  /health`.
- Документация в `docs/`.
- Smoke-тесты в `tests/`.

Код работает: можно создавать дашборд по自然ному запросу и редактировать его через HTTP API.

## 2. Главная цель следующих этапов

Превратить рабочий прототип в стабильный продуктовый микросервис:

1. Надежность и наблюдаемость.
2. Качество AI-генерации и редактирования.
3. Поддержка всех нужных типов визуализаций.
4. Production-like dashboard как у DataLens Demo.
5. Готовность к интеграции с Laravel.

## 3. Приоритет 1 — надежность и продакшен-готовность

### 3.1. Откат объектов при ошибке (saga/cleanup)
**Проблема:** если генерация чарта упала посередине цикла, в DataLens остаются «осиротевшие» подключение и уже созданные чарты.

**Нужно сделать:**
- В `dashboard_service.create_ai_dashboard` собирать ID созданных объектов:
  - connection_id;
  - chart_ids;
  - dashboard_id.
- Обернуть весь цикл в try/except; при ошибке удалять все успешно созданные объекты через `DataLensClient`:
  - `delete_ql_chart(chart_id)`;
  - `delete_connection(connection_id)`;
  - если дашборд успел создаться — удалить его.
- В ответе об ошибке возвращать `detail` с понятным текстом.
- Добавить флаг `cleanup_on_error: bool = True` в запрос `POST /api/dashboards/generate`, чтобы в режиме отладки можно было не удалять.

**Обсудить:** удалять ли автоматически объекты в DataLens при ошибке редактирования.

### 3.2. Структурированное логирование
**Сейчас:** в основном `print()`.

**Нужно:**
- Перейти на `logging` во всех модулях;
- Логи писать в stdout в JSON- или простом текстовом формате;
- Добавить request-id для каждого HTTP-запроса;
- Логировать:
  - старт/конец генерации;
  - какие таблицы выбраны;
  - сколько SQL валидны/невалидны;
  - сколько попыток исправления;
  - ID созданных объектов;
  - ошибки DataLens и LLM с трейсбеком в файл/stdout.

### 3.3. Обработка ошибок API
- Все внешние вызовы обернуть в try/except;
- Из `DataLensError` формировать корректный HTTP-ответ:
  - 502, если DataLens недоступен;
  - 504, если LLM не ответил;
  - 400, если пользовательский запрос пустой;
  - 500 — внутренние ошибки.
- Не возвращать сырые трейсбеки в HTTP-ответ (только в логи).

### 3.4. Таймауты
- Для запросов к LLM — настройка `LLM_TIMEOUT` (уже есть, проверить);
- Для DataLens client — добавить отдельный `DATALENS_TIMEOUT`;
- Если запрос не укладывается — возвращать понятную ошибку.

### 3.5. Dockerfile и docker-compose для datalens-ai
**Цель:** поднимать сервис одной командой вместе с DataLens.

**Нужно:**
- Написать `Dockerfile` на основе `python:3.11-slim`;
- Установить зависимости из `requirements.txt`;
- Запускать `uvicorn main:app --host 0.0.0.0 --port 8100`;
- Добавить сервис `datalens-ai` в `datalens/docker-compose.yml` или дать отдельный `docker-compose.override.yml`;
- Пробросить `.env`;
- Учесть, что LLM может быть как в контейнере, так и на хосте.

**Обсудить:** должен ли LLM запускаться в отдельном контейнере или на хосте через GPU.

## 4. Приоритет 2 — качество AI

### 4.1. Выбор таблиц и графиков
**Сейчас:** LLM выбирает таблицы из списка ключевых, иногда выбирает малоинтересные или пустые.

**Нужно улучшить:**
- В промпт `chart_one.md` включать:
  - пример данных по каждой таблице (1–2 строки);
  - самые «полезные» поля;
  - явно запрещать таблицы с 0 строк;
- Разнообразить типы графиков: не все `line` подряд;
- Учитывать сообщение пользователя: если просят «топы» — table, «динамика» — line, «распределение» — column;
- Добавить эвристику выбора: если есть timestamp — line; если есть count/sum/avg по категориям — column; если есть имя + метрика — table.

### 4.2. Проверка осмысленности (sanity check)
**Откладывалась ранее, теперь нужна.**

**Идея:** после того как план готов, сделать быстрый отдельный вызов LLM или программные проверки:
- все графики возвращают больше 0 строк;
- SQL действительно использует запрошенную таблицу;
- типы данных соответствуют chart type (для line первая колонка — date/timestamp);
- нет графиков-дублей с одинаковым SQL;
- нет бессмысленных заголовков;
- секции логично сгруппированы.

Если что-то не так — либо перегенерировать конкретный график, либо понизить его приоритет.

**Обсудить:** делать sanity check программно (быстро, надежно) или через вторую LLM (медленнее, но умнее). Скорее всего, сначала программно.

### 4.3. Лучшие секции и заголовки
- Заголовки графиков должны быть конкретными;
- Секции группировать по темам: «Активность», «Качество», «Пользователи», «Финансы» и т.п.;
- Не создавать секцию из одного графика, если это не нужно;
- Убрать пустые/общие названия вроде «Overview», если есть более точные.

### 4.4. Улучшение редактирования
Сейчас LLM может:
- не понять, какой график «первый»;
- удалить не тот график;
- проигнорировать часть запроса.

**Нужно:**
- Передавать в промпт список графиков с номерами и ID;
- Явно указывать: «график 1 — это первый в списке, его ID ...»;
- Для операций удаления/перестановки требовать подтверждения через `chart_id`;
- Поддерживать нечеткие ссылки: «график про отзывы», «вторая диаграмма»;
- Если LLM не уверен — не выполнять удаление, а вернуть уточняющий вопрос (в будущем).

### 4.5. Работа с FK и JOIN
- В схему передаются связи, но LLM не всегда их использует;
- Добавить в промпт пример правильного JOIN по FK;
- Запретить выдуманные внешние ключи;
- Если нужен JOIN, LLM должна использовать только поля из раздела «Связи».

## 5. Приоритет 3 — типы визуализаций

### 5.1. Metric / KPI карточки
**Зачем:** чтобы дашборд был как Demo — 4–7 KPI в ряд вверху.

**Шаги:**
1. Изучить JSON реальных metric-чартов из `samples/demo/charts/`:
   - `Charts: Indicator_1.json`;
   - `Demo: Sales.json`;
   - `Demo: Clients.json`.
2. Понять, это QL или wizard charts (у metric в Demo был `metric_wizard_node`, нужен dataset).
3. Если для QL metric невозможен — изучить, можно ли создать dataset программно или использовать простой виджет-таблицу с одной цифрой.
4. Добавить шаблон `metric` в `ql_chart_builder.py`, если возможно.
5. Добавить раскладку KPI в `dashboard_builder.py`: до 7 карточек в ряд шириной 5 каждая.

**Обсудить перед реализацией:** KPI требуют dataset, а его создание сложнее QL. Возможно, для MVP KPI пока не делать, а потом реализовать через wizard+dataset. Решение нужно зафиксировать.

### 5.2. Pie / donut
- Взять образец из `samples/demo/charts/*Pie_chart*`;
- Проверить, поддерживается ли пирог через QL;
- Добавить в `ql_chart_builder.py` тип `pie`;
- Правила: первая колонка — категория, вторая — число.

### 5.3. Bar (горизонтальные столбцы)
- Аналогично column, но `bar`;
- Хорошо подходит для топов;
- Использовать образец `Bar_chart*.json`.

### 5.4. Area
- Почти как line, но с заливкой;
- Образец `Area_chart*.json`.

### 5.5. Селекторы/фильтры на дашборде
**В Demo есть** селекторы (Date, Region).

**Нужно:**
- Изучить, как selector-виджеты описаны в JSON дашборда;
- Понять, как они связываются с графиками;
- Если это сложно — отложить;
- Если возможно — добавить селектор по дате на динамических дашбордах.

### 5.6. Расширение ColumnInfo/ChartType
- Добавить новые значения в `models/schema.py:ChartType` (`PIE`, `BAR`, `AREA`, `METRIC`);
- Обновить `ALLOWED_TYPES` в `sql_pipeline.py`;
- Обновить нормализацию типов в `ql_chart_builder.py`.

## 7. Приоритет 5 — интеграция с Laravel (фронт не в этой задаче)

### 7.1. Авторизация между Laravel и datalens-ai
**Сейчас:** CORS открыт для всех, авторизации нет.

**Нужно:**
- Добавить shared token через заголовок, например `X-API-Key`;
- В `.env` параметр `SERVICE_TOKEN`;
- Все endpoint'ы кроме `/health` требуют токен;
- Документировать в `docs/API.md`.

### 7.2. Асинхронная генерация
**Проблема:** генерация дашборда может занимать 30–90 секунд, HTTP-запрос может отвалиться.

**Варианты:**
- Фоновая задача с ID job:
  - `POST /api/dashboards/generate` возвращает `job_id`;
  - `GET /api/jobs/{job_id}` — статус;
- Или SSE-стриминг прогресса.

**Обсудить с Laravel-разработчиком**, какой вариант удобнее. Скорее всего, фоновая задача + опрос статуса.

### 7.3. Хранение ссылок
В Laravel нужна таблица (ее будет делать Laravel-AI):
- id;
- user_id;
- datalens_id;
- title;
- connection_id;
- created_at.

В `datalens-ai` свое состояние хранить не обязательно.

### 7.4. CORS
Ограничить список источников через `CORS_ORIGINS` в `.env`.
